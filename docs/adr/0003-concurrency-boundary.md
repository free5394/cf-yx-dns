# 3. 同步的并发边界

日期：2026-11-05
状态：已接受

## 背景

一次同步分两段：先按一次 `list_records` 的快照算出差量计划，再按计划逐条写入。写入期间不再回读，源码里也没有锁或条件更新（见 `src/cf_yx_dns/cf_records.py` 的 `plan_sync` 与 `apply_sync`）。所以两轮同步重叠时，可能各自基于同一份旧快照算出「要新增 X」，然后都去新增 X。

重复创建的后果比「下一轮会收敛」更糟：`compute_diff` 只删除「内容不在目标集合里」的记录（`src/cf_yx_dns/cf_records.py:111`），内容相同的两条记录都在目标集合里，因此**都不会被删除**——重复记录会一直留着，直到这个 IP 掉出目标集合、两条一起被删。

## 决策

1. **Actions 内部靠 workflow 级 `concurrency` 串行**：`group` 是固定字符串 `dns_cf_push`，与触发方式无关，所以本工作流的定时（schedule）与手动（workflow_dispatch）两类触发共用同一个队列；`cancel-in-progress: false` 表示正在跑的那轮不被取消，后来的排队等待（`.github/workflows/dns_cf.yml`）。**范围仅限本工作流的这两类触发**：别的 workflow、以及本工作流将来新增的 `push` 等触发都在保护之外。
2. **同组只保留一个 pending 运行**：这是 GitHub 的行为，连着触发三次时中间那次会被顶掉。可以接受：每一轮都重新读取记录并重算差量，跳过中间那次不丢目标状态，丢的只是一次冗余执行。
3. **本地手动运行不在保护范围内**：本地进程和 Actions 任务之间没有任何互斥。要在本地调试就先停掉定时任务，或接受可能产生的重复记录并手工清理。
4. **加 `timeout-minutes` 兜底**：挂住的运行会长期占住 group，而同组只保留一个 pending，表现为「定时任务悄悄不再执行」。超时让队列强制释放。注意超时的语义是**强制取消**而非失败，见「后果」里关于告警的说明。
5. **不引入分布式锁或作业级互斥**：工具规模不支持，也没有可共享的锁介质（本地与 CI 之间尤其没有）；用排队加超时覆盖已知的真实场景即可。
6. **不为超时/取消场景引入告警兜底**：可以把告警步骤的条件改成 `failure() || cancelled()`，但用户手动取消运行同样会走取消路径，于是每次手动取消都会误报一次「同步失败」；拆独立告警 job 或接外部监控，对一个每天只跑四次的工具属于用复杂度过拟合。取舍是接受「超时只能从 Actions 运行记录发现」这一点，并把口径写进 README 与「后果」。

## 后果

- 正常运维路径（定时 + 手动）不会重叠，重复创建的窗口被关闭。
- 本地并行运行仍可能造出重复记录，且这类记录不会被后续同步清理掉，需要人工删除。
- 一旦某轮运行超过 15 分钟会被**强制取消**。取消不等于失败：`if: failure()` 的推送告警步骤在这种情况下**不保证执行**，所以超时场景可能既没有同步结果、也没有告警，只能从 Actions 运行的红色记录里发现。
  这块的兜底**已决定不做**（见决策 6），属于已接受的残留风险：超时只表现为 Actions 里一次红色运行，不会有推送。若将来确实需要，再评估 `failure() || cancelled()`（代价是手动取消会误报）、独立告警 job 或外部监控三种路径。
